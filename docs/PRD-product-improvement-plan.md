## Problem Statement

Sciath is a CRA compliance automation platform for embedded Linux. It hooks into build systems (Yocto primarily) to extract firmware artifacts and run hardware-aware vulnerability scans. The target user is a stressed embedded/firmware engineer at a device manufacturer facing the EU CRA September 2026 reporting deadline.

The platform already has strong foundations: a 7-layer hardware-aware CVE filter engine (validated 0 FP, 0 FN), Article 13 PDF generation, VEX import/export, and a working CLI + dashboard. But three features need improvement to reach product-market fit:

1. **VEX Justifier** (8/10 → 9+/10): Hardware-aware filtering works but the output doesn't tell the "wow" story
2. **CRA Readiness Dashboard** (7/10 → 9+/10): Data exists but lacks the single "shippable / not shippable" verdict
3. **CVE-to-Patch Pipeline** (1/10 → meaningful MVP): Detection exists but no remediation guidance

## Demand Evidence

Conversations with embedded/firmware engineers at device manufacturers. Primary pain confirmed across multiple conversations:

- **False positive CVE triage**: Days spent investigating CVEs that don't apply to their hardware configuration
- **Documentation burden**: Manual compliance report generation for CRA
- **Legacy maintenance**: Embedded devices with 10+ year security patching needs, 2010-era codebases needing patches for today's threats, with no active dev team. This is the highest-urgency segment.

No users yet (pre-product). Demand is conversation-validated, not behavior-validated.

## Status Quo

Embedded firmware engineers currently:
- Run Yocto's `cve-check` class, get 800+ CVEs, manually triage each one
- Cross-reference kernel .config by hand to determine if a subsystem is even enabled
- Write justification documents manually in Word/PDF
- Maintain spreadsheets tracking which CVEs apply to which product variants
- Spend 2+ days per release on CVE triage that could be automated

Tools available to them: Yocto cve-check (detection only), generic SCA tools (Snyk, Grype — no hardware awareness), platform-locked solutions (Kontron KontronOS, Torizon — require their OS).

Nobody else is doing kconfig + DTB + PACKAGECONFIG-aware CVE filtering with automated VEX justification export.

## Target User & Narrowest Wedge

**Target user**: Embedded/firmware engineer at a device manufacturer (IoT, industrial, medical, automotive). Managing products in maintenance mode with 10+ year lifecycles. Small team or solo. Facing CRA September 2026 reporting deadline.

**Narrowest wedge**: The combo demo narrative:
1. "Here are 847 CVEs in your SBOM" (panic)
2. "341 after Kconfig suppression, 89 exploitable on this hardware, 12 need your attention" (relief)
3. "Here's your Article 13 compliance report with suppression rationale" (victory)

This narrative IS the product. All three improvements serve it.

## Constraints

- **September 2026 CRA reporting deadline** — 5 months from now. Everything must ship before this.
- **Solo founder / small team** — must be efficient with build scope
- **Pre-product** — need to validate with real users while building
- **Yocto-first** — other build systems gated on customer demand
- **Zero false negatives** — better to include an artifact than miss a CVE match
- **Non-blocking by default** — build plugins must never fail a build due to Sciath errors

## Premises

1. The combo demo (847 → 341 → 89 → 12 → compliance report) is the wedge product. All three improvements serve this narrative.
2. Hardware-aware filtering (kconfig/DTB/PACKAGECONFIG) is the real differentiator, not "another SBOM scanner." Double down on this, don't broaden to generic SCA.
3. The 10-year maintenance mode use case (legacy embedded devices) is the highest-urgency segment. Least capacity, most CVE noise.
4. CVE-to-Patch includes both recipe version bumps (greenfield) AND backport patch identification (legacy BSPs). Phase 1 ships version bump recommendations + "here are the upstream commits that fix this CVE" for backport cases. Actual patch generation is a future phase. *(Revised after cross-model challenge: legacy teams on pinned silicon vendor BSPs can't just bump versions without breaking board support.)*
5. The CRA September 2026 reporting deadline is the forcing function.

## Cross-Model Perspective

Three independent voices reviewed the strategy:

**Claude subagent** steelmanned Sciath as "the only CRA compliance platform that understands what your hardware actually runs." Key insight: the product's center of gravity should be the compliance report and audit trail, not the build integration. Legacy teams need "point at firmware, get defensible compliance package." Challenged P4 (recipe bumps too narrow for pinned BSPs) — premise was revised.

**External voice #1** ("CVE Triage Terminal"): The instant wow is the output delta tied to actual config — 847 → 341 → 89 → 12. That fourth number is what nobody else shows. The CLI terminal output with tiered numbers is "the shareable screenshot that goes viral in embedded Slack channels." POC pitch: show up with their BSP already scanned.

**External voice #2** ("CRA Command Center"): Build a release-centric "CVE cockpit" not a generic dashboard. Core output should be "312 CVEs in SBOM, 7 potentially relevant, 2 exploitable in this device profile, 3 mitigated by config/VEX, 2 need patching before ship." Position as "The CRA command center for embedded releases."

**Convergence:** All three independently identified the tiered suppression numbers as the wow moment and the audit artifact as what closes the sale.

## Approaches Considered

### Approach A: Demo-First Sprint
Summary: Polish the combo demo as a single end-to-end flow. Actionable CVE-to-Patch report (no automation). 6-8 weeks.
Effort: M | Risk: Low
Pros: Fastest to validation, minimal over-building, proves narrative works
Cons: CVE-to-Patch stays manual, dashboard stays basic, may feel incomplete to prospects

### Approach B: Platform-Complete (CHOSEN)
Summary: Build all three features to production quality in parallel. Full VEX polish, CRA cockpit dashboard, CVE-to-Patch with version bumps + backport identification. 12-16 weeks.
Effort: L | Risk: Medium
Pros: Most complete product for September deadline, covers full combo demo narrative, strongest competitive position
Cons: Risk of over-building before user validation, tight timeline

### Approach C: Wedge + Viral Loop
Summary: Free CLI for VEX filtering, paid dashboard + CVE-to-Patch. 4+10 weeks.
Effort: M | Risk: Medium
Pros: Best distribution strategy, gets tool in hands fast
Cons: More complex GTM, may cannibalize paid features

## Recommended Approach

**Approach B: Platform-Complete**, structured as three parallel workstreams with a shared milestone: the combo demo working end-to-end by week 6.

## Workstream 1: VEX Justifier (8/10 → 9+/10)

**Goal:** Make the filtering story visible, shareable, and emotionally compelling.

### What's missing (the gap from 8 to 9+)

The engine works. The output doesn't tell the story. A user runs a scan and gets filtered results, but they don't SEE the journey from 847 → 12. They don't get a one-screen summary of "why" each CVE was suppressed. The before/after is invisible.

### Improvements

**1.1 Tiered suppression waterfall (CLI + Dashboard)**
Add a "suppression funnel" to scan output showing CVE count at each filter layer:

```
Scan Results: rpi4-gateway (kirkstone, armv7)
================================================
  Raw CVEs from SBOM:              847
  After build-time filter:         612  (-235 packages not on device)
  After Kconfig suppression:       341  (-271 subsystems disabled)
  After DTB device tree filter:    267  (-74 peripherals not present)
  After PACKAGECONFIG filter:      189  (-78 features not enabled)
  After busybox applet filter:     156  (-33 applets not compiled)
  After patch detection:            98  (-58 already backported)
  After custom policy rules:        89  (-9 org-specific exclusions)
================================================
  ACTION REQUIRED:                  89
    Critical (CVSS >= 9.0):          2  <<<
    High (CVSS >= 7.0):            10
    Medium:                        41
    Low:                           36
    In CISA KEV:                    1  <<<
```

This is the "shareable screenshot." Every embedded Slack channel should want to post this.

**Implementation:** Add `suppression_funnel` field to scan status API response. Each filter layer already tracks its count. Wire the counts into `OutputFormatter` in the CLI and the dashboard scan detail view.

**API response schema for `suppression_funnel`:**
```json
{
  "suppression_funnel": {
    "raw": 847,
    "layers": [
      {"name": "build_time", "remaining": 612, "suppressed": 235, "label": "packages not on device"},
      {"name": "kconfig", "remaining": 341, "suppressed": 271, "label": "subsystems disabled"},
      {"name": "dtb", "remaining": 267, "suppressed": 74, "label": "peripherals not present"},
      {"name": "packageconfig", "remaining": 189, "suppressed": 78, "label": "features not enabled"},
      {"name": "busybox", "remaining": 156, "suppressed": 33, "label": "applets not compiled"},
      {"name": "patch", "remaining": 98, "suppressed": 58, "label": "already backported"},
      {"name": "custom_policy", "remaining": 89, "suppressed": 9, "label": "org-specific exclusions"}
    ],
    "action_required": 89
  }
}
```
If a filter layer was skipped (e.g., no DTB provided), it appears with `"suppressed": 0` and `"label": "skipped — no DTB uploaded"`. Layers are never omitted from the array.

**Files touched:**
- `sciath-backend: sciath/engine/pipeline.py` — collect per-layer counts during analysis
- `sciath-cli: sciath_cli/output.py` — render the waterfall in terminal
- `sciath-backend: api/routers/scans.py` — include funnel in status response
- `sciath-backend: templates/scans/detail.html` — render funnel as visual bar chart

**1.2 Per-CVE suppression rationale**
For every suppressed CVE, a one-liner explanation:

```
CVE-2024-1234: SUPPRESSED — CONFIG_BLUETOOTH not set (kirkstone/rpi4/.config:2847)
CVE-2024-5678: SUPPRESSED — SPI controller not present in device tree (am335x.dtb)
CVE-2024-9012: SUPPRESSED — backport patch applied (meta-security/recipes-kernel/linux/cve-2024-9012.patch)
```

This is CRA evidence. Each line traces to a specific build artifact.

**Implementation:** Assessment model already has `applied_filter_layers` and justification fields. Add a `suppression_rationale` text field that concatenates: filter layer name + specific evidence (config symbol, DTB node path, patch file path). Expose in CLI `--explain` mode (already exists, enhance with artifact paths) and in the compliance report.

**Files touched:**
- `sciath-backend: sciath/engine/filters/*.py` — each filter returns rationale string with artifact reference
- `sciath-backend: assessments/models.py` — add `suppression_rationale` field
- `sciath-cli: sciath_cli/commands/assess.py` — enhance `--explain` output
- `sciath-backend: sciath/reports/*.py` — include rationale in Article 13 PDF and VEX exports

**1.3 Confidence scoring visibility**
Show WHY each remaining CVE matters. For the 89 that survived filtering:

```
CVE-2024-3456 | openssl 3.0.2 | CVSS 9.8 | EPSS 0.87 | IN KEV
  Why it matters: Package present, version in affected range, no
  config-based mitigation found, actively exploited (CISA KEV)
  Recommended: Upgrade to openssl 3.0.15+ or apply backport
```

**Implementation:** The `--explain` mode exists but only shows filter reasoning. Add "why it survived" explanation for unfiltered CVEs — invert the logic. For each remaining CVE, list which filters it PASSED and why.

**1.4 Architecture-aware filtering (STRETCH GOAL)**
Add CPU architecture as a filter signal. CVEs targeting x86-specific instructions don't apply to ARMv7. CVSS attack vectors (`AV:P` physical, `AV:L` local) combined with deployment context.

This is a new filter layer, not a presentation improvement. It belongs in a stretch goal because the data source is unresolved (NVD CPE architecture coverage is spotty). **Phase 1 approach:** hand-curated mapping of ~20 well-known architecture-specific CVE families (e.g., Spectre/Meltdown x86 variants, ARM TrustZone-specific issues). Parse CVSS `AV:P` vector as a cheap additional signal. Expand the mapping over time.

**Implementation:** Parse `CVSS:3.1/AV:X` from EnrichedCVE. Cross-reference with scan's `yocto_machine` → architecture mapping. New filter layer between DTB and custom policy.

**Files touched:**
- New: `sciath-backend: sciath/engine/filters/architecture.py`
- `sciath-backend: sciath/engine/pipeline.py` — register new filter layer
- `sciath-backend: intelligence/models/` — architecture → CVE family mapping (start with curated JSON file)

### VEX Score: 9+/10 when complete

The gap between 8 and 9+ is entirely about visibility. The engine already works. These changes make the story visible, shareable, and auditable.

## Workstream 2: CRA Readiness Dashboard (7/10 → 9+/10)

**Goal:** Single-screen "is this release CRA-shippable?" answer.

### What's missing (the gap from 7 to 9+)

The dashboard shows scan data but doesn't answer the question the user is actually asking: "Can I ship this?" The data is there. The verdict isn't.

### Improvements

**2.1 CRA Readiness Verdict — the big red/green signal**

Top of every scan detail page, a single verdict:

```
┌─────────────────────────────────────────────┐
│  CRA READINESS: NOT READY                    │
│  ████████████████░░░░  78% compliant         │
│                                              │
│  Blockers:                                   │
│  ✗ 2 Critical CVEs unresolved (Art. 13.8)   │
│  ✗ 1 CISA KEV entry open (Art. 11)          │
│  ✓ SBOM generated (Art. 13.1)               │
│  ✓ VEX justifications documented (Art. 14)  │
│  ✓ 758/847 CVEs triaged with rationale      │
│                                              │
│  [Fix blockers]  [Generate report anyway]    │
└─────────────────────────────────────────────┘
```

When all blockers clear:

```
┌─────────────────────────────────────────────┐
│  CRA READINESS: SHIPPABLE ✓                  │
│  ████████████████████  100% compliant        │
│                                              │
│  ✓ 0 Critical/High CVEs unresolved           │
│  ✓ 0 CISA KEV entries open                   │
│  ✓ SBOM generated (SPDX 2.3)                │
│  ✓ All suppressions documented with VEX      │
│  ✓ Article 13 Technical File ready           │
│                                              │
│  [Download CRA Evidence Pack]                │
└─────────────────────────────────────────────┘
```

**Implementation:** New `CRAReadinessService` that computes verdict from:
- Open CVEs above severity threshold (configurable, default: Critical-only blocks the verdict; High CVEs appear as warnings but do not block. CISA KEV entries always block regardless of CVSS severity.)
- CISA KEV status
- SBOM presence and quality score
- VEX documentation completeness (% of suppressions with rationale)
- Report generation status

**Compliance percentage formula:** `percentage = (passed_checklist_items / total_applicable_checklist_items) * 100`. All items weighted equally. "Out of scope" items are excluded from the denominator. A blocker does NOT cap the percentage. The percentage reflects documentation/triage completeness, while blockers independently control the SHIPPABLE/NOT READY verdict. Example: 78% means 7 of 9 applicable items passed, but the 2 failures happen to be blockers.

**Failure modes:** If SBOM is missing, verdict is "INCOMPLETE — no SBOM uploaded." If scan analysis is still running, verdict is "PENDING." If external data (NVD/EPSS) is stale (>24h), verdict includes a warning but does not block. CRAReadinessService never throws — it always returns a verdict, even if degraded.

**Files touched:**
- New: `sciath-backend: sciath/cra/readiness.py` — verdict computation
- `sciath-backend: api/routers/scans.py` — add `/scans/{id}/cra-readiness/` endpoint
- `sciath-backend: templates/scans/detail.html` — render verdict widget
- `sciath-cli: sciath_cli/commands/scan.py` — add `--cra-check` flag to CLI

**2.2 CRA Article mapping**

Map each checklist item to the specific CRA article it satisfies:

**Canonical CRA article checklist (definitive, not illustrative):**

| Requirement | CRA Article | Sciath coverage | Dynamic status source |
|---|---|---|---|
| Software Bill of Materials | Art. 13(1) | Full | SBOM presence + quality score |
| Default security settings | Art. 13(2) | Partial | Kconfig analysis (hardening flags) |
| Unique product identification | Art. 13(5) | Full | Project + release version label |
| Known vulnerability disclosure | Art. 13(6) | Full | Assessment count + triage % |
| Vulnerability handling process | Art. 13(8) | Full | Open Critical/KEV count |
| Security update mechanism | Art. 11 | Out of scope | N/A (OTA is outside Sciath's domain) |
| Timely security updates | Art. 11(2) | Partial | Remediation recommendations exist |
| Coordinated vuln disclosure | Art. 14 | Full | VEX export available |
| Contact info for vuln reporting | Art. 13(5b) | Out of scope | N/A (organizational, not tooling) |

Items marked "Out of scope" appear in the checklist as greyed-out with explanation, so users know Sciath intentionally does not cover them (vs. missing coverage).

**Implementation:** Static mapping of CRA articles to Sciath checklist items. Dynamic status from scan data. This is mostly a presentation layer change.

**2.3 Release-centric view (CVE Cockpit)**

Reframe the dashboard around releases, not scans. A "release" is a named firmware build (e.g., "rpi4-gateway v2.3.1") that may have multiple scans over time.

```
Release: rpi4-gateway v2.3.1 (kirkstone)
Scans: 3 (latest: 2026-04-01)

CVE Trend:
  2026-03-15:  92 action items
  2026-03-22:  47 action items (45 resolved)
  2026-04-01:  12 action items (35 resolved)

CRA Status: 78% → needs 2 more fixes
```

**Implementation:** Project model already exists. Add a `Release` concept (name + version + target machine) that groups scans. Dashboard view shows releases as the primary navigation, with drill-down to scans.

**Decision:** Start with scan grouping by `project + version_label` (no new model). Add `version_label` and `target_machine` fields to `Scan`. Dashboard groups scans with matching `(project_id, version_label)` into a release view. Migrate to a first-class `Release` model later if the grouping approach becomes limiting.

## Workstream 3: CVE-to-Patch Pipeline (1/10 → Meaningful MVP)

**Goal:** For each unresolved CVE, tell the developer exactly what to do. Don't just list problems, recommend fixes.

### What to build (Phase 1 — recommendations, not automation)

**3.1 Remediation recommendations per CVE**

For each of the 12 "action required" CVEs, show:

```
CVE-2024-3456 | openssl 3.0.2 → 3.0.15
  Fix type: VERSION BUMP
  Current: openssl_3.0.2.bb (meta-oe/recipes-connectivity/openssl)
  Target:  openssl 3.0.15 (fixes CVE-2024-3456, CVE-2024-3457)
  Yocto recipe: PREFERRED_VERSION_openssl = "3.0.15"
  Risk: LOW — patch version bump, same API

CVE-2024-7890 | linux-yocto 6.1.21
  Fix type: BACKPORT NEEDED
  Current: linux-yocto 6.1.21 (meta-rpi BSP layer, pinned)
  Upstream fix: kernel commit abc123f ("fix UAF in net/bluetooth")
  Backport: Cherry-pick abc123f onto 6.1.x branch
  CVE-CHECK status: Patched in 6.1.38+
  Risk: MEDIUM — kernel backport, requires testing

**Risk classification (semver-based, no API compatibility check in Phase 1):**

| Risk | Criteria | Examples |
|---|---|---|
| LOW | Patch version bump (x.y.Z) | openssl 3.0.2 → 3.0.15, curl 7.88.0 → 7.88.1 |
| MEDIUM | Minor version bump (x.Y.z) or kernel backport | openssl 3.0.x → 3.1.x, linux cherry-pick |
| HIGH | Major version bump (X.y.z) or cross-major kernel upgrade | glibc 2.31 → 2.38, linux 5.10 → 6.1 |
```

**Implementation:**

For VERSION BUMP recommendations:
- Query NVD/OSV for "fixed in version" data (already in EnrichedCVE)
- Compare current version (from SBOM) with fix version
- Determine if it's a minor bump (low risk) or major bump (high risk)
- Generate the Yocto variable override suggestion

For BACKPORT identification:
- **Data source:** The kernel security team publishes CVE-to-commit mappings at `git.kernel.org/pub/scm/linux/security/vulns.git/`. This repo contains structured YAML files mapping CVE IDs to fix commits, affected version ranges, and stable branch backport status. Parse this rather than grepping the full kernel git history.
- Sync the vulns.git repo periodically (daily cron, ~5MB repo)
- Extract commit hash and one-line summary from the YAML mapping
- Cross-reference with CVE-CHECK patched-in-version data (already in Yocto cve-check output)
- Flag whether the fix exists in a stable branch that matches the user's kernel version
- **Scope:** Backport finder is kernel-only in Phase 1. Userspace packages (openssl, curl, glibc, etc.) always get VERSION BUMP recommendations, not backport suggestions. There is no equivalent structured CVE-to-commit mapping for userspace packages.
- **Failure mode:** If vulns.git is unreachable or CVE has no mapping, show "No upstream fix commit identified — manual investigation required" with a link to the NVD entry. Never block on missing data.

**Files touched:**
- New: `sciath-backend: sciath/remediation/recommender.py` — recommendation engine
- New: `sciath-backend: sciath/remediation/version_advisor.py` — version bump analysis
- New: `sciath-backend: sciath/remediation/backport_finder.py` — kernel vulns.git parser
- `sciath-backend: api/routers/assessments.py` — add remediation field to assessment response
- `sciath-cli: sciath_cli/commands/assess.py` — show recommendations in output
- `sciath-backend: templates/assessments/detail.html` — render recommendations

**3.2 Remediation priority matrix**

Sort the action items by effort vs. impact:

```
PRIORITY MATRIX — rpi4-gateway v2.3.1

Quick Wins (low effort, high impact):
  1. openssl 3.0.2 → 3.0.15    [version bump] fixes 3 CVEs
  2. curl 7.88.0 → 7.88.1      [version bump] fixes 1 Critical

Needs Investigation:
  3. linux-yocto CVE-2024-7890  [backport] kernel bluetooth UAF
  4. busybox CVE-2024-4321      [config change] disable affected applet

Long-term:
  5. glibc CVE-2024-9999        [major upgrade] requires glibc 2.38+
```

**Implementation:** Score each recommendation by composite priority score:

```
priority_score = fix_type_weight * 10 + cvss_max + (5 if in_kev) + cve_count
```

| Fix type | Weight | Rationale |
|---|---|---|
| Version bump (patch) | 4 | Lowest effort, highest confidence |
| Config change | 3 | Low effort but may affect functionality |
| Version bump (minor) | 3 | Moderate effort, API changes possible |
| Kernel backport | 2 | Requires testing, may not apply cleanly |
| Major upgrade | 1 | Highest effort, likely breaks things |

Sort descending. Higher score = do this first. Ties broken by CVSS descending. This formula can be tuned later, but gives engineers a concrete starting sort order.

**3.3 Actionable output formats**

Generate machine-readable remediation output:

```bash
# For CI/CD integration
sciath assess list --format remediation-json

# For Yocto developers — generates a .bbappend snippet
sciath remediate suggest --format yocto

# For project managers — CSV for tracking
sciath remediate suggest --format csv
```

The Yocto format outputs:

```bitbake
# Auto-generated by Sciath — fixes CVE-2024-3456, CVE-2024-3457
PREFERRED_VERSION_openssl = "3.0.15"
```

**Implementation:** New output format in `OutputFormatter`. The Yocto snippet generator is simple string templating for version bumps.

### CVE-to-Patch Score: ~5/10 when complete (Phase 1)

This gets from 1/10 to "meaningful." It doesn't auto-apply patches, but it tells the developer exactly what to do and in what order. That alone saves hours per release.

**Phase 2 (9+/10) would require:** Auto-generating `.bbappend` files with version bumps, running test builds in a sandboxed Yocto environment, creating PRs against the BSP layer repo, and tracking which CVEs a patch actually resolves post-build. That is a separate design doc.

## Failure Modes

Each new service degrades gracefully. Sciath never blocks on missing external data.

| Service | External dependency | On failure | User sees |
|---|---|---|---|
| Suppression funnel | None (computed locally) | N/A | Always works |
| CRAReadinessService | Scan analysis complete | Shows "PENDING" | Clear status |
| Remediation recommender | NVD/OSV "fixed in" data | Shows "unknown fix version" | Actionable note |
| Backport finder | kernel vulns.git | Shows "manual investigation required" | Link to NVD |
| Evidence pack | Report generation (WeasyPrint) | Generates without PDF, includes other artifacts | Partial ZIP with note |
| Architecture filter | Curated mapping file | Skips layer, shows "skipped" in funnel | Zero suppression, not zero info |

## Testing Strategy

Each workstream has dedicated test coverage. The existing test suite (813 unit + 19 validation + 21 UI tests) is the baseline.

**Workstream 1 (VEX):**
- Unit tests for suppression funnel aggregation (all layers present, some skipped, empty scan)
- Unit tests for rationale string generation per filter type
- Snapshot tests for CLI waterfall rendering (Rich output)
- Validation: re-run existing 36-label ground truth fixtures, verify funnel counts match

**Workstream 2 (Dashboard):**
- Unit tests for CRAReadinessService (all-clear, blocked, incomplete, degraded states)
- Unit tests for release grouping logic
- UI tests for verdict widget rendering
- Integration test: upload → analyze → check CRA readiness endpoint

**Workstream 3 (CVE-to-Patch):**
- Unit tests for version comparison (minor bump, major bump, pinned BSP)
- Unit tests for vulns.git YAML parser (valid mapping, missing CVE, malformed YAML)
- Mock tests for NVD/OSV "fixed in" data (present, absent, partial)
- Integration test: scan with known CVEs → verify recommendations match expected fixes

**Reference fixture (canonical demo + test baseline):**
- Board: Raspberry Pi 4 Model B
- Yocto: poky kirkstone 4.0.x (latest point release at build time)
- Layers: meta-raspberrypi, meta-openembedded (meta-oe, meta-python, meta-networking)
- Image: core-image-base with `INHERIT += "create-spdx cve-check"`
